# 探针验证报告：无 editor_sdk / 无 Office 生成可编辑 DOCX

> 日期：2026-10-11
> 目的：验证「便携 + 轻量」路线的**核心技术假设**是否成立
> 位置：`spike/portable_export_probe/`
> 结论：**✅ 成立** —— 用 Python 标准库即可产出含原生 OMML 公式的 DOCX，Word 与 WPS 双端均可编辑

---

## 一、要验证的假设

「便携 + 轻量」路线成立的前提是：**能脱离 `editor_sdk` 与 Office 生成可编辑公式的 DOCX**。
若这一条不成立，整个便携路线就不成立。故先做探针，**不在生产代码上试错**。

| 编号 | 假设 |
|---|---|
| H1 | 仅用 Python 标准库（`zipfile` + 手写 OOXML）即可产出合法 DOCX |
| H2 | 公式是**原生 OMML**（`word/document.xml` 内含 `<m:oMath>`） |
| H3 | 不含 `word/embeddings/*`（非 OLE 对象）、无图片冒充 |
| H4 | Word 能打开且不报错 |
| H5 | 公式被识别为**原生 Word 公式**（`doc.OMaths.Count > 0`），而非图片/OLE |
| H6 | **实际修改公式内部字符 → 保存 → 关闭 → 重开 → 改动保留** |

> H6 的判定标准照搬项目铁律：**判定"公式可编辑"必须实际改公式内部字符→保存→重开→比对**，
> 不能用"有 OMML 节点"或"能打印"代替。

## 三、一个值得记录的方法论教训

**第一次 H6 测试失败了，但失败的是测法，不是产品。**

- **错误测法**：用 `doc.OMaths(1).Range.Text = "新文本"` **整体覆写**公式。
  → 结果：公式被**拆散成 6 个**、内容丢失。
- **原因**：`Range.Text` 赋值是 COM 的**粗暴覆写**，会破坏公式内部结构。
  **它测的是"用代码覆写公式"，不是"用户在公式里改一个字"。**
- **正确测法**：`rng.Characters(7).Text = "3"` —— **就地替换单个字符**，这才等价于用户行为。
  → 结果：改动保留、公式结构完好。

> **教训**：验证"可编辑性"时，**验证动作必须等价于真实用户动作**。
> 用程序化的粗暴操作去测，得到的是"程序能不能覆写"，而不是"用户能不能改"。
> 这与项目既有教训同源——**"结构上覆盖"不算验证通过**。

## 四、结论

### ✅ 已证明（本次实测）

1. **便携路线的核心技术假设成立**：不依赖 `editor_sdk`、不依赖 Office，**用 Python 标准库**即可生成含原生 OMML 公式的 DOCX。
2. **公式是真原生**：Word 与 WPS 双端均识别为 `OMath`（`InlineShapes=0`，非图片、非 OLE）。
3. **公式真的可编辑**：双端均通过"改字符→保存→重开→比对"。
4. **体积极小**：最小样例 1,282 字节；生成逻辑**零第三方依赖**。

### ⚠️ 尚未证明（需后续验证）

| 项 | 说明 |
|---|---|
| **完整版式保真** | 探针只验证了公式。项目历史踩过的坑（`<a:graphicData>` 缺 `uri`、TAB 控制字符、HTML 实体、制表位、题号双重渲染）**尚未在自研生成器上验证** |
| **图片行内位置** | 图片插入与行内定位未测（已知现状是"统一居中附题干后"） |
| **LaTeX → OMML 的自动转换** | 探针是**手写 OMML**；真实场景需要从题库里的 LaTeX 自动转换（本项目公式为 LaTeX 存储） |
| **跨机器便携** | 需在第二台机器验证（本次未做） |
| **打包体积** | 未实测（预估 ~80–120 MB） |
| **性能** | 未测（大批量题目的生成耗时） |

### 下一步

1. **实现最小 LaTeX → OMML 转换器**，覆盖项目实际用到的符号集（可从 `bank` 的公式表统计频次）。
2. **扩展探针**：加图片、制表位、多题排版，逐个复现历史坑并解决。
3. **打包实测**：验证体积与跨机器便携。
