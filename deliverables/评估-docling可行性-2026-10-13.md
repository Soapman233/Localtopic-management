# 评估：能否用 docling 的技术路线「识别试卷」

**日期**：2026-10-13
**触发**：用户反馈「识别试卷存在问题」，并问能否用 docling 的技术路线。
**方法**：**对照实验**（不是讨论）—— 同一批真实试卷，docling 与当前自研链路各跑一遍，比数据。
**探针**：`spike/probe_docling.py`（可重复执行）；产物 `spike/_probe_docling.md` / `.json`
**环境**：docling **2.138.0**（已在本机 `envs/docling` 就绪）+ 真实交付库（7945 题 / 17771 公式）

---

## 一、结论（先给结论，再给证据）

> **docling 不能替代当前链路** —— 它会在**占 67% 的 MathType 公式**上失效，
> 而「公式可编辑」正是本项目唯一不能让步的硬要求。
>
> **但它有 3 个值得单独评估的用途**（见 §四），其中**「PDF/扫描件」是最有价值的一个**——
> 那是当前链路**完全做不了**的事。

---

## 二、决定性证据：docling 对两种公式的处理完全不同

### 对照实验（两份真实试卷，同一套探针）

| | 样本 A：压强浮力计算题 | 样本 B：电学档位题 |
|---|---|---|
| 源文件 `oleObject` 数 | **49** | **0** |
| 源文件 WMF/EMF（公式显示图） | 47 | — |
| 源文件 `word/media` 图片 | 71 | — |
| 库里该文件的公式 `kind` | **mathtype 49 条** | **omml 1091 条** |
| **docling 产出 `FormulaItem`** | **0** ❌ | **1056** ✅ |
| docling markdown 里 `$` 次数 | **0** ❌ | **2182** ✅ |
| docling markdown 里 `<!-- image -->` | **72** | 少量 |
| docling 耗时 | 转换 **0.9s** | 转换 **1.2s** |

**样本 B 的 docling 输出（真 LaTeX）**：
```
1.如图甲所示，电源电压恒定， $R_{1}$ 是定值电阻， $R_{2}$ 是最大阻值为 $20 \Omega$
的滑动变阻器，灯泡 $L$ 的额定电压为 $6V$ ，其 $I-U$ 图像如图乙所示
```

**样本 A 的 docling 输出**（同一位置，公式不见了）：
```
1．如图所示，水壶内装入200g的水，水深10cm，水壶的底面积为15cm 2 ，取 *g* =10N/kg
```
（`15cm 2` —— 上标被压平成普通字符；**没有 `$…$`、没有 `FormulaItem`**）

### 为什么是这个结果（技术原因）

| 公式形态 | 在 DOCX 里是什么 | docling 能否处理 |
|---|---|---|
| **OMML**（Office Math） | **XML**（`<m:oMath>`，纯文本节点） | ✅ **能**——直接解析成 LaTeX |
| **MathType OLE**（`Equation.DSMT4`） | **OLE 复合文件**（二进制，头 `D0CF11E0`），里面是 MTEF 字节流 | ❌ **不能**——它没有 MTEF 解码器；OLE 对象只能当"嵌入对象"，于是**降级成图片或纯文本** |

**docling 没有 MTEF 解码器**，这不是配置问题、不是版本问题——是它的能力边界。

### 本项目的真实分布（这决定了权重）

```
mathtype（旧式 OLE）  11863 条   67%
omml                 5908 条   33%
```

→ **docling 路线会丢掉约 2/3 的公式。** 而项目硬要求是
**「导出公式必须可编辑，公式图片不算达标」**（源试卷约 80% 含 MathType）。
**这一条一票否决。**

## 三、当前链路 vs docling（逐项对照）

| 维度 | 当前自研链路 | docling |
|---|---|---|
| **MathType OLE → LaTeX** | ✅ 自研 `mtef_conv.py`（vendor `mtef-py`，精确解码非 OCR，成功率 99.69%） | ❌ **无能力** |
| OMML → LaTeX | ✅ `pipeline/omml.py`（质量与 docling 相当，见下） | ✅ 1056 条，`$R_{1}$` / `$20 \Omega$` |
| **题目切分**（第 1 题…第 2 题） | ✅ `segment.py`（题号识别、大题分组） | ❌ **不提供**——只给文档结构（段落/标题/表格/图片），**切题逻辑仍要自己写** |
| 图片 | ✅ 从 `word/media` 按 `sha256` 精确取用 | 🟡 只给 `PictureItem` + `<!-- image -->` 占位，**要自己回原始 zip 取字节** |
| 表格 | ❌ **不提取** | ✅ **`TableItem`**（样本 A 1 个 / 样本 B 3 个） |
| PDF / 扫描件 | ❌ **不支持**（只吃 DOCX） | ✅ 支持（含 OCR / 版面模型） |
| 速度（单文件） | 阶段1 全量 209 份已跑完（`outputs/preprocess_final/`） | **0.9–1.2s/份**（DOCX 不加载 ML 模型；导入 4.2s） |
| 依赖体积 | 无额外模型 | 带 ML 模型（PDF 路线会显著变大） |
| 与现有产出契约 | 已产出 9,765 题的 JSON，**导出/组卷/前端全依赖它** | 需要**整套重写**数据层与下游 |

**OMML 部分的 LaTeX 质量对比**（同一道题）：
- 当前链路：`R_{1}` / `20Ω` / `I−U`（Unicode 字符）
- docling：`$R_{1}$` / `$20 \Omega$` / `$I-U$`（LaTeX 宏）
→ **两者都可用**（`Ω` 与 `\Omega` 在 KaTeX/OMML 里等价）。**docling 在这一档没有明显优势。**

## 四、docling 真正值得评估的 3 个用途

| # | 用途 | 价值 | 成本 |
|---|---|---|---|
| **1** | **PDF / 扫描试卷**——当前链路**完全做不了**（只吃 DOCX）。老师手里有大量 PDF 卷子 | 🔴 **最高**（是**新增能力**，不是替换） | 中（需接 OCR/版面模型；公式仍是图片，除非另配 PDF 公式识别） |
| **2** | **表格提取**——当前链路不提取表格，docling 给 `TableItem` | 🟡 中 | 低（作为**补充**，与主链路并存） |
| **3** | **OMML 公式的交叉校验**——两条独立实现互校，可发现 `omml.py` 的漏读 | 🟢 低—中 | 低（离线比对，不进主流程） |

> ⚠️ **注意用途 1 的天花板**：PDF 里的公式**同样是图片**（PDF 没有 OLE/OMML）。
> 所以「PDF 路线」能满足**看卷/找题**，但**不满足「导出公式可编辑」**——
> 除非再叠加专门的 PDF 公式识别（那是另一个量级的投入与准确率风险）。

---

## 五、建议

1. **不要用 docling 替换当前识别链路**——会丢掉 2/3 的公式（MathType），
   而这是本项目唯一不能让步的要求。**这条不建议推进。**
2. **如果要解决「识别试卷存在问题」，先定位问题在哪一层**（见 §六）——
   docling 只可能覆盖其中一层，**用它当"通用解药"会跑偏**。
3. **值得单独立项的是「PDF/扫描件支持」**（用途 1）：那是**新增能力**，
   与现有 DOCX 链路**并存**而非替换。
