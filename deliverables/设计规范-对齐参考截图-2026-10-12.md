# 设计规范：对齐参考截图的全站 UI 重构

> 日期：2026-10-12
> 依据：用户提供的 6 张界面截图（前 4 张为 ONES Wiki 风格文档应用，后 2 张为任务管理工具）

---

## 一、从截图提炼的设计语言

6 张截图的共同点（= 要吸收的部分）：

| 维度 | 共同做法 |
|---|---|
| **外壳** | 左侧导航 + 顶部工具条 + 内容区，**三层结构清晰**；内容区是绝对主角 |
| **配色** | **白色/浅灰表面为主**，蓝色只作**强调色**（按钮、链接、选中态），不大面积铺 |
| **导航** | 选中项是**圆角胶囊 + 淡主色底 + 左侧强调条**；分组有**小号弱化的区域标签** |
| **层级** | 页面标题大而粗（~32px）→ 灰色元信息行 → 分区标题（~20px）→ 正文 14px/1.8 行高 |
| **容器** | 卡片有**头部行**（标题 + 右侧元信息），行分隔线极淡 |
| **状态** | 语义化 Chip（橙/绿/红/灰）表示状态，**颜色 + 文字**双通道 |
| **交互** | 右侧可折叠上下文面板；创建流程用**滑出面板**；搜索带 `⌘K` 提示 |
| **留白** | 内容区左右留白充足，段落间距明显 |

**要规避的不足**（截图里确实存在的问题）：

| 问题 | 出处 | 规避做法 |
|---|---|---|
| 主区大面积留白、信息密度过低 | 截图 5 | 本应用是数据密集型工具，**不追求「空」，追求「疏朗但不空」** |
| 下拉菜单溢出到屏幕外被裁切 | 截图 4 | 菜单/弹层必须做边界收敛（MUI 默认已处理，但自定义弹层要检查） |
| 右侧动态面板文字长、无断行 | 截图 1 | 长文本 `overflow-wrap`，面板内不放大段正文 |
| 任务行字号过小（12px 密排） | 截图 2 | 表格正文保持 ≥13px，行高 ≥36px |

## 二、🔴 一条硬约束：**亮蓝用不了**

截图的主色是亮蓝（约 `#2B7FFF`）。但本项目的对比度门禁里有一条：

```
["onSolid", "primary", 4.5, "浅色·主按钮/顶栏 白字 on 主色底"]
```

**`#2B7FFF` 上的白字只有约 3.7:1，达不到 AA 正文要求的 4.5:1**，会直接把门禁打挂。

**因此的处理**（这也是本轮的关键设计决策）：

> **不靠「把蓝色调亮」去还原观感，而是靠「把表面调白、把中性色分层」去还原。**

主色保持当前对比度安全的深蓝（`#2F63EA`），观感上更接近截图的**克制、专业**，
而不是靠高饱和抢注意力——后者恰恰是截图**没有**做的事。

## 三、本轮已实施的改动（外壳层，一处生效全站）

| # | 模块 | 改动 | 理由 |
|---|---|---|---|
| 1 | **顶栏 AppBar** | 实心品牌蓝 → **纸面白 + 1px 底部分隔线**，文字转深色 | 截图里没有一个是「大面积色块顶栏」。内容区（表格/题干）才是主角，顶栏抢视觉重量会让人累 |
| 2 | **侧栏 Drawer** | 白底 → **页面底色（浅灰）+ 右侧 1px 分隔线** | 与白色内容区形成**柔和**分界，替代重阴影（截图同款做法） |
| 3 | **导航项 ListItemButton** | 通栏色块 → **圆角胶囊 + 左右 8px 留边** | 通栏选中块会让侧栏「糊成一片」；胶囊化后侧栏更透气（截图标志性做法） |
| 4 | **选中态** | 淡主色底 + **左侧 3px 主色强调条**（`::before`，不占布局） | 强调条提供**非颜色**的定位线索，对色觉障碍更友好 |
| 5 | **分组标签 ListSubheader** | 小号 + 加字距 + 大写 + 弱化 | 只做「区域标签」，不与导航项抢注意力（截图同款） |
| 6 | **Chip** | 加 `fontWeight: 500` | 状态徽章在密排列表里要能一眼扫到 |

**已验证**：`tsc` 0 错误｜对比度 **65/65 通过**｜**288 项测试全过**｜构建成功

## 五、响应式方案（桌面 + 移动）

| 断点 | 布局 |
|---|---|
| **≥1200px（桌面）** | 侧栏常驻（240px）+ 内容区全宽（工具页）/ 限宽（正文页）+ 可折叠右侧面板 |
| **900–1200px（小桌面/平板横）** | 侧栏常驻但收窄；右栏折叠为抽屉 |
| **600–900px（平板竖）** | 侧栏转 **temporary Drawer**（已有）+ 顶栏汉堡菜单（已有） |
| **<600px（手机）** | 单栏；页面留白 16px；表格转**卡片列表**或横向滚动；触控目标 ≥44px |

**已具备的基础**：侧栏在窄屏已是 `temporary`；页面留白 `p: { xs: 2, sm: 3, md: 4 }`；
`img/video max-width:100%` 防溢出；`-webkit-text-size-adjust` 防 iOS 聚焦缩放。

**待补**：表格在 <600px 的降级（当前依赖 `TableContainer` 横向滚动，可接受但不优雅）；
组卷页在手机上的双栏必然降为单栏（需确认拖拽在触屏可用）。

## 六、技术选型与理由（用户要求说明）

### 结论：**保持 React 18 + Vite 5 + TypeScript + MUI 5，不换栈**

| 层 | 选型 | 理由 |
|---|---|---|
| **前端框架** | React 18 + TypeScript | 已在用，10 个页面 + 288 项测试都在其上。换框架的**视觉收益为零**（截图里的界面任何框架都能做），但会带来跨 10 页的重写风险 |
| **构建** | Vite 5 | 构建 8–9s，产物已按需分包（vendor-react/mui/data/katex/motion）。轻量且快 |
| **UI 库** | **MUI 5.18** | ⚠️ 关键：MUI **本身就是 Google Material Design 的官方实现**，与本轮「往 Google 设计语言靠」的目标**同源**，不需要引入新体系 |
| **样式** | MUI `sx` + 主题 token | 项目**曾用过 Tailwind 并已移除**（`theme.ts` 有留痕：两套 token 冗余、全库 0 处使用工具类）。**重新引入 Tailwind 会重蹈覆辙** |
| **动效** | AutoAnimate（~2KB）+ 原生 View Transitions | 上一轮已接入并分包。**不引入 Framer Motion**（~30KB+，本应用不需要编排级动效） |
| **后端** | Python + FastAPI + SQLite | 本地单用户应用，**无并发压力**；换后端没有任何收益。且打包后 65MB 已含运行时 |
| **打包** | PyInstaller onedir | 已跑通（绿色免安装）。换技术栈会丢掉已验证的「双击即用」形态 |

### 明确**不建议**引入的

| 技术 | 为什么不用 |
|---|---|
| **Tailwind CSS** | 项目已移除过；与 MUI 主题 token 双轨冗余 |
| **shadcn/ui / Radix** | 是 Tailwind 生态，会连带引入 Tailwind；且需重写全部组件 |
| **Ant Design** | 视觉语言与目标（Google 风）不一致，且体积更大 |
| **Framer Motion** | 体积 30KB+，本应用只需列表增删 + 路由淡入 |
| **Next.js / SSR** | 本地单用户应用，不需要 SEO/SSR，徒增复杂度 |

### 轻量化与性能的现状（实测）

| 指标 | 值 |
|---|---|
| 打包体积 | **65.4 MB**（含 Python 运行时；前端静态资源仅占约 1.5 MB） |
| 首屏 JS | 入口 38.4 KB + vendor-react 205 KB + vendor-mui 322 KB + vendor-data 92 KB + vendor-misc 66 KB |
| 冷启动 | 1.65 s（双击到可访问） |
| 前端构建 | 约 9 s |

> **诚实说明**：入口 JS **38,368 字节**，超出实施方案设定的 30,800 字节门禁约 25%。
> 该门禁基于重构前的代码设定，与「信息架构精简 + M3 主题 + 动效」的范围存在张力。
> 若要严格守住，需把导航/标题表拆成懒加载模块（代价是侧栏首帧延迟）——**建议重新评估该门禁**。
