# 上线就绪度评估（2026-10-11）

> 口径：本文回答「正式上线还缺什么」。
> 所有结论基于对当前仓库与交付库的**实测核对**（命令见文末），非文档转述。

---

## 0. 先分清「上线」的两种含义

本项目存在**两个不同的目标口径**，答案完全不同，不能混为一谈：

| 口径 | 含义 | 当前状态 |
|---|---|---|
| **A. 单人本地** | 一名老师在**自己电脑**上用，仅本机 `127.0.0.1:8720` | 🟢 基本就绪，差 3 件小事 |
| **B. 10 人团队** | 约 10 名教师**共享使用**（项目原始需求） | 🔴 **远未就绪**，是「正式上线」的主要工作量 |

> 项目自身的定位是「私有本地题库组卷系统」，但**原始需求是服务约 10 名教育工作者**。
> 若「正式上线」指后者，则缺口集中在**权限、网络、并发、数据分发**四块。

---

## 1. 场景 A：单人本地 —— 基本就绪

核心闭环（检索 → 组卷 → 预览 → 导出原生 OMML，Word/WPS 双端可编辑）已实测通过，
后端 373 项 / 前端 26 项测试全绿，交付库零污染。**只差以下 3 件**：

| # | 缺口 | 现状 | 影响 |
|---|---|---|---|
| A1 | **Git 推送凭据** | 本机无 token / SSH key / `gh`；11 次提交已就绪 | 仓库推送不了（你授权即可解决） |
| A2 | **启动器不可移植** | `启动题库.bat` 硬编码 `C:\Users\SOAP\.workbuddy-ai\...\kb\Scripts\python.exe`，换机器回落到裸 `python`（依赖可能不全） | 换机/给他人会起不来或报缺依赖 |
| A3 | **首次运行不「开箱即用」** | 需手动 `bank.cli init` + 导入才能建库；`bank.db`（62 MB）未随仓库分发 | 老师无法自助起步 |

**补充建议**：Word/WPS 全页人工核对仍只覆盖了学生版前 2 页 + 程序化校验，
上线前建议逐页肉眼过一遍（尤其答案解析版）。

## 2. 场景 B：10 人团队 —— 真正的缺口（🔴）

这是「正式上线」的主要工作量。按阻塞程度分级：

### 🔴 阻塞级（不解决无法多人用）

| # | 缺口 | 实测依据 | 为什么阻塞 |
|---|---|---|---|
| B1 | **无权限体系** | `grep -rniE "auth\|login\|password\|jwt" webui/` **零命中**；前端无登录界面 | 谁都能删卷、改元数据、导出；无法区分「只读老师」与「管理员」 |
| B2 | **无异地 / 局域网访问** | `webui/config.py:53` `DEFAULT_HOST="127.0.0.1"`，注释明确「只监听回环」 | 10 人要么各自装一份（数据割裂），要么一台机做服务器（当前不支持对外监听） |
| B3 | **并发形态未解决** | editor_sdk 桥接**必须串行**（并发即 `WinError 10048` 端口占用，已记入项目记忆） | 两人同时导出会互相阻塞/报错；组卷导出是高频动作 |
| B4 | **客户端环境依赖重** | 每台机器都需 `editor_sdk`（端口 39099）+ Word 或 WPS；缺则导出不可用 | 10 台机器逐一安装配置，运维成本高、易出错 |
| B5 | **数据分发与同步未定义** | `bank.db` 62 MB、`.gitignore` 排除；无同步方案 | 集中一份还是各持一份？改了库怎么同步？无答案 |

### 🟠 影响体验级（能上线但难用）

| # | 缺口 | 实测依据 |
|---|---|---|
| B6 | **元数据欠账严重** | `difficulty` **100% 为「未标注」**；`grade` 有效仅 44/209（21%）、`textbook` 39/209（19%）、`chapter` 53/209（25%）；答案 50%、解析 58% |
| B7 | **「按维度筛题」实际不可用** | 因 B6：按年级筛只见约 21% 的题，难度筛选完全无数据 → 只能靠关键词检索 |
| B8 | **题库管理能力缺失** | 无 UI 导入入口、无收藏夹、无智能组卷、无去重 → 更像「预置题库的组卷器」，不是能自我生长的知识库 |

### 🟡 技术债 / 可观测性（长期）

| # | 缺口 | 实测依据 |
|---|---|---|
| B9 | 前端单 chunk **1,058 kB** 无代码分割 | 首屏加载偏慢 |
| B10 | **无错误监控 / 日志采集** | 生产可观测性为零，出问题只能靠老师口述 |
| B11 | **无备份 / 恢复流程文档** | 有 `verify_backup` 工具，但无定期备份与恢复 SOP |
| B12 | `\begin{array}` 环境（全库 1 条公式）桥接不支持 | 导出降级为「（公式）」占位并告警 |

## 3. 建议的最小上线路径

**Phase 1 · 单人本地（1–2 天）**
1. 配置 Git 凭据并推送（`git push -u origin main && git push origin --tags`）
2. 修 `启动题库.bat` 的可移植性（`BANK_PY` 优先 + `requirements.txt` 安装指引）
3. 提供首启向导或随包分发 `bank.db`
4. Word/WPS 逐页人工核对

**Phase 2 · 小团队（1–2 周，若要做 10 人）**
1. 局域网部署（`--host 0.0.0.0` + 内网地址 + 防火墙规则）**或** 单机共享方案
2. 轻量权限（至少「只读 / 可编辑」两级）
3. 导出任务队列串行化（把 B3 的并发限制变成服务端排队，而非报错）
4. 数据集中（一台机持有 `bank.db`，其余走 HTTP）

**Phase 3 · 数据治理（持续）**
1. 难度 / 年级 / 教材标注工作流（教研组人工，UI 已有复核队列雏形）
2. 题库导入入口（Word/Excel）——把「预置库」变成「可生长库」

---

## 4. 一句话结论

> **以「单人本地」口径：只差推送凭据、启动器可移植性、首启数据分发三件小事，即可上线。**
> **以「10 人团队」口径（项目原始需求）：真正的缺口是权限、局域网访问、并发串行化、数据分发四块基建，外加元数据治理；这是「正式上线」的主要工作量，不是收尾工作量。**
