## 二、逐项方案

### T3-1 断点统一 + 1366×768 双栏

**现状**（`PaperBuilderPage.tsx:183`）：
```ts
const narrow = useMediaQuery('(max-width:1439px)')
```
1366×768（教师笔记本主流分辨率）命中 `narrow` → 右栏（**默认排版视图**）被折叠进
**默认关闭**的抽屉（`:573-583`）。而《流程重构设计》Q8 明确要求「默认排版视图」——
**在最常见的屏幕上，核心的「边组边看」默认看不见**。

**方案**：
- 统一到 MUI 标准断点，**移除 1439 魔法值**：
  - `lg`（≥1200px）**保持双栏**；
  - `<lg` 才折叠右栏为抽屉；
  - 右栏最小宽度 360px（现在 layout 视图固定 640、list 固定 420）。
- 右栏宽度改为**随视口自适应**：`clamp(360px, 38vw, 640px)`。
- 1366 下右栏 ≈ 519px，结果区仍 ≥ 600px（远超此前推算的 166px）。
- 补充：`<lg` 时给一行「建议 ≥1200px 使用双栏」的轻提示。

**验收**：1366×768 浏览器实测**默认双栏且排版视图可见**；1200/1440/1920 三档无横向滚动条。

### T3-2 门禁体验重写（🔴 最高风险）

**红线（不可违反）**：
> `uiStore` 的门禁语义 —— `previewFresh` / `previewDegradedOk` / `previewRevision` 票据校验 /
> `previewSettings` 设置键 / `previewContent` 内容摘要 / `previewAllowed`
> （`uiStore.ts:99-140`）—— **行为一个字节都不能变**。
> 本任务**只改「怎么说、怎么显示、入口在哪」**，不改「能不能导出」的判定。

**现状问题**（方案 §2.2 P0-2）：
- 门禁是**会话态**（刷新即锁，`uiStore.ts:144` 明确不持久化）→ 老师会困惑「为什么按钮是灰的」；
- 两个入口（导出抽屉 / 导出中心）显示同一门禁但**行为与文案不同**；
- 文案曾是「降级解锁」「门禁已解锁」（阶段 1 已中文化，但**结构**未改）。

**方案**（表达层）：
1. **单一入口原则**：明确「导出抽屉」是组卷页的**唯一**导出入口；
   导出中心（`/export`）定位为**全屏预览 + 导出历史**，并在其中提示「回到组卷页可边看边导」。
2. **把门禁状态讲成一句话**：用阶段 1 的 `describeExportGate(state)` 统一三态文案
   （`ready` / `locked` / `degraded`），**所有位置同源**。
3. **锁定态给出可执行动作**：不止说「已锁定」，而是**直接给「生成预览」按钮**
   （当前需老师自己找到预览入口）。
4. **刷新即锁的困惑**：在锁定提示里**说明原因**——「预览结果不跨页面刷新保留，请重新生成」。
   （不改「刷新即锁」的行为，只解释它。）
5. **进度**：预览/导出改用 `ProgressStages`（阶段 2 已建），给阶段 + 上限预期。

**验收**：
- 门禁语义测试（既有 + 新增）全绿；
- 浏览器实测：未预览 → 导出被拦且**界面直接给出「生成预览」**；预览后 → 可导出；
- **不得**出现「同一状态下两个入口说法不同」。

### T3-3 抽 `useQuestionFilters`

**现状**：`SearchPage.tsx:170-212` 与 `PaperBuilderPage.tsx:168-208` **近乎逐行相同**的
「关键词 300ms 防抖 + `readFiltersFromUrl` + `writeFiltersToUrl` + `queryParams`/`facetsParams` useMemo」，
合计约 **80 行重复**。

**方案**：新建 `src/hooks/useQuestionFilters.ts`，返回
`{ keywordInput, setKeywordInput, filters, setFilters, page, setPage, queryParams, facetsParams, reset }`，
两页共用。**行为必须完全一致**（含防抖 300ms、URL `replace`、页码归 1 的时机）。

**验收**：两页筛选/搜索/分页行为无变化（浏览器实测 + 既有测试）。

### T3-4 「我的试卷」全站可达

**现状**：`PaperSwitcher` 只在**组卷页顶部**（`PaperBuilderPage.tsx:468`）；
其余页面想换试卷必须先去组卷页。试卷列表还藏在左侧抽屉（`:586-641`）。

**方案**：把 `PaperSwitcher` 提升到**全局 `AppBar`**（`App.tsx`），
使其在任意页面都能切换/新建试卷。组卷页顶部**移除重复的切换器**（保留「筛选/试卷面板/导出」按钮）。

**验收**：任意页面顶部可切换试卷；切换后组卷页/导出页同步（`paperStore` 为唯一来源）。

## 三、视觉基线机制（本阶段新增）

### 3.1 问题

阶段 1/2 的基线截图放在 `.tmp_verify/`（**未入库**）。阶段 3 会**真实改变视觉**
（双栏布局、门禁表达），必须有可靠的「改前/改后」对照，否则无法区分「预期变化」与「回归」。

### 3.2 方案：**脚本入库 + 基线图不入库 + 清单入库**

| 项 | 位置 | 是否入库 | 理由 |
|---|---|---|---|
| 采集脚本 | `frontend/tests/visual/capture.mjs` | ✅ | 小文本，是机制的一部分 |
| 比对脚本 | `frontend/tests/visual/compare.py` | ✅ | 只依赖 PIL/numpy（项目 Python 环境已有） |
| 使用说明 | `frontend/tests/visual/README.md` | ✅ | 含**更新策略** |
| 基线图 | `.tmp_verify/baseline-<tag>/*.png` | ❌ | 每阶段都变、属派生产物；入库会让「接受一次视觉变化」提交约 2MB 二进制 |
| **基线清单** | `frontend/tests/visual/baseline-manifest.json` | ✅ | 记录**页面名 + sha256 + 采集参数 + 时间** → 基线何时被替换，在 git 里**可见可审计** |

**更新策略（写进 README）**：
> 只有当视觉变化被**人工渲染看图确认**之后，才允许用 `capture.mjs` 覆盖基线并更新 manifest。
> 禁止「为了让比对变绿而更新基线」。

### 3.3 判定口径

| 指标 | 阈值 | 含义 |
|---|---|---|
| `mean_diff` | < 1.0 | 无可见变化 |
| `pct_gt32` | < 0.5% | 无结构性变化 |
| 度量自校验 | 自比 == 0 | 保证度量本身没写错 |

**任何超阈值的页面，都必须「渲染出来看」并在报告里说明是预期变化还是回归。**
