## 一、版本拆分：两个版本，一个内核

### 1.1 核心设计决策

**不复制两份代码。** `bank/`（题库·组卷·导出）、`pipeline/`（DOCX 结构化）、`webui/`（API）、
`frontend/`（界面）是同一套业务逻辑；复制会「修一个 bug 改两处、跑两套测试」，必然长期漂移。
因此采用**「一个内核 + 两个版本外壳」**，版本差异全部收敛到 `webui/edition.py`。

### 1.2 目录分类

```
editions/
├── README.md                    分类总览：对照表 / 如何选择 / 如何切换 / 线上版硬约束
├── local/                       版本一：本地运行版
│   ├── README.md                    使用说明（面向老师）
│   ├── 启动题库.bat                  可移植一键启动（BANK_PY > .venv > PATH）
│   └── settings.example.json         设置示例
└── online/                      版本二：线上部署版
    ├── README.md                    部署指南（架构 / 硬约束 / 步骤 / 鉴权 / 备份 / 限制）
    ├── .env.example                 环境变量模板
    ├── start-server.bat             Windows 宿主启动（推荐）
    ├── nginx.conf                   反向代理 + Basic Auth
    ├── Dockerfile                   （可选）Linux 容器，导出不可用
    ├── docker-compose.yml           （可选）一键编排
    └── requirements.linux.txt       （可选）跨平台依赖子集
```

### 1.5 线上版的三条硬约束（已在文档中如实声明）

1. **必须 Windows 宿主**：`requirements.txt` 含 `pywin32`，且导出依赖 `editor_sdk` + Word/WPS 的 COM 自动化。
   Linux 容器只能提供浏览/检索/组卷/结构预览（Dockerfile 已明确标注「导出不可用」）。
2. **导出必须串行**：桥接单实例，并发调用报 `WinError 10048`；**无服务端导出队列**（已知限制）。
3. **鉴权为「访问控制」级**：共享口令，**无**用户/角色/审计体系（后续阶段）。

## 三、前端完整分析与重构方案（摘要）

完整文档：`deliverables/前端完整分析与重构方案-2026-10-11.md`（503 行）。

### 3.1 现状判断

> 当前前端是**工程质量偏高、产品可用性偏低**的内部工具：类型安全干净（tsc 通过、0 个 `@ts-ignore`）、
> 状态设计克制、导出门禁已收敛为单一实现；但**把「开发者视角的技术真相」直接暴露给老师**
> （`scan index`、`snapshot_digest`、门禁、降级解锁），且**信息架构是「功能平铺」而非「任务流」**。

**用户「面向大众可用性低、需大规模重构」的判断成立**，但重构重点应是
**信息架构 + 术语/交互 + 两版适配**，而**不是**推倒技术栈重写。

### 3.2 五项 P0 可用性问题

| # | 问题 | 位置 |
|---|---|---|
| P0-1 | **术语外泄**：`scan index` / `snapshot_digest` / `body_paragraph_number` 直接显示给老师 | `ExportDiagnostics.tsx:25-28,99-100` |
| P0-2 | **门禁心智负担 + 双重入口**：灰按钮拦住「导出」，文案看不懂 | `ExportDrawer.tsx:124-132`、`ExportPage.tsx:117-126` |
| P0-3 | **1366×768 核心体验不可见**：右栏（默认排版视图）被折叠进**默认关闭**的抽屉 | `PaperBuilderPage.tsx:179,463-473` |
| P0-4 | **检索页与组卷页职责重叠**：都能搜题加题但能力不同，老师不知该在哪页 | `SearchPage.tsx` vs `PaperBuilderPage.tsx` |
| P0-5 | **难度筛选是死功能**：难度 100% 未标注，筛不出结果会误判「系统坏了」 | `FilterSidebar.tsx:41` |

### 3.3 两个关键发现

1. **Tailwind 是挂名依赖**：全库 26 处 `className` 中 **0 处**使用 Tailwind 工具类；
   `tailwind.config.js` 的 token 与 `theme.ts` 重复且都无消费方。→ **建议直接移除**（零样式回归）。
2. **测试基座是最大风险**：现有 26 项是「源码字符串断言」（无 DOM、无 Testing Library），
   重构一改结构即失效。→ **阶段 0 必须先建真实组件测试**。

### 3.4 六阶段重构方案（每阶段结束系统可用）

| 阶段 | 目标 |
|---|---|
| 0 | **护栏先行**：vitest 测试基座 + ErrorBoundary + 全局 toast + queryKey/errors 收敛 |
| 1 | **术语与 IA**：`glossary.ts` 术语中文化 + 导航分组 + 默认落地页改 `/builder` |
| 2 | **设计系统统一**：移除 Tailwind、token 单一来源、四态规范 |
| 3 | **主流程重构**（最高风险）：1366 双栏 + 门禁体验重写 + 消除检索/组卷重复 |
| 4 | **两版适配**：`AuthProvider` + `RequireAuth` + `usePermission` + 只读态 |
| 5 | **性能与无障碍**：路由级 `lazy` + `manualChunks` + a11y 基线 |

**明确不做**：迁移 shadcn/Radix、引入 Redux、移动端专门适配、所见即所得公式编辑器、推倒重写任何页面。
