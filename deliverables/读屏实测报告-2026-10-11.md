## 1. 方法

### 1.1 为什么是「hook 语音模块」而不是别的

技能已说明自动化只能覆盖约 1/3–1/2 的 WCAG 失败，故必须用真实读屏。
真实读屏的难点在**捕获 NVDA 到底念了什么**。NVDA 是 GUI 程序、需要交互式桌面，
且语音经合成器输出。我选择**方案 A（NVDA 全局插件 hook 语音）**：

- NVDA 内部**所有**语音（焦点播报、live region、对象导航……）最终都汇集到
  `speech.manager.SpeechManager.speak(speechSequence, priority, ...)`。
  我在插件里替换该方法，在调用原实现前把序列里的字符串拼接落盘。
- 因此捕获到的是 **NVDA 真正决定要念的内容**，而不是「浏览器无障碍树」（后者是方案 C，
  本次**未使用**）。

**hook 有效性证明**：插件在 `__init__` 里主动 `speech.speakMessage("SRVERIFY SELFTEST 12345")`，
该语句出现在日志中 → 说明 hook 生效、捕获链路通畅：

```
1791715550.681  META  speechlog add-on plugin __init__
1791715550.682  MGR   SRVERIFY SELFTEST 12345
```

### 1.2 插件安装结构（team-lead 指出的「静默不加载」坑，已踩并修）

NVDA 只认 `addons/<包名>/` + `manifest.ini`。第一次 `manifest.ini` 的
`description` 里含**英文逗号**，被 configobj 解析成 **list**，NVDA 报
`Manifest file has errors.` 并**静默跳过**（日志里只有一行 WARNING）。去掉逗号后正常加载：

```
DEBUG - addonHandler._getAvailableAddonsFromPath: Loading add-on from ...\addons\speechlog
DEBUG - addonHandler: Found add-on speechlog - 1.0. Requires API: (2020, 1, 0). Last-tested API: (2026, 2, 0)
DEBUG - addonHandler: Addon speechlog added to globalPlugins package path
```

> 教训（与 team-lead 的判断一致）：**不要假设插件加载了**，必须查 `nvda.log` 的 addon 行。

### 1.3 让 NVDA 真的跑起来

- 首次运行会弹欢迎向导 → 预置 `%APPDATA%\nvda\nvda.ini`（`showWelcomeDialogAtStartup=False`、
  `askedAllowUsageStats=True`）绕过。
- `nvda.exe`（启动器）会因**残留单实例互斥量**而直接退出、不产生任何日志；
  改直接运行 **`nvda_noUIAccess.exe`** 并显式指定 `-c <配置目录> -f <日志> --debug-logging`。
- NVDA 与浏览器必须处于**交互式会话**（本机 `Console` 会话 3）；进程确实起来了
  （`nvda_noUIAccess.exe ... Console 3`）。

### 1.4 让 NVDA 跟踪浏览器窗口（本次最大的工程难点）

NVDA 跟踪的是 **OS 前台窗口**。`page.bringToFront()` 只激活标签页、不置前台。
本机是**共享的、有人在用的**机器，其它窗口（含 WorkBuddy 自身——它也是
`Chrome_WidgetWin_1`，即 Electron）会不断抢走前台。

- 写了 `focus_chromium.py` / `refocus_loop.py`：枚举 `Chrome_WidgetWin*` 顶层窗口，
  用 **AttachThreadInput + ALT 解锁 + SetWindowPos 置顶再取消** 强制前台。
- 目标窗口用 **ASCII 标记 `Google Chrome for Testing`** 唯一识别
  （中文 argv 会被控制台代码页损坏，导致匹配失败——已踩坑）。
- 有界循环（约 90s）持续把浏览器顶到前台。

## 4. 发现的问题

### 4.1 「对话框」角色词未被念出（有对照实验，暂判为 NVDA 侧行为）

- DOM 有 `role="dialog"` + `aria-labelledby`，且用 **CDP 无障碍树**确认**计算角色就是 dialog**：
  ```
  DRAWER AX: [{"role":"dialog","name":"切换试卷","ignored":false}]
  EXPORT AX: [{"role":"dialog","name":"导出 · 八年级物理·浮力与压强单元测验","ignored":false}]
  ```
- 但 NVDA 播报里**只出现名字、没有「对话框」这个词**。
- **对照实验**：写了一个**最小参照页**（`.tmp_verify/nvda_sr/dialog_test.html`）：
  `<div role="dialog" aria-labelledby tabindex="-1">`，`focus()` 到该 div。NVDA 播报为：
  ```
  测试对话框
  标题 2 级  测试对话框
  这是一个最小的 role 等于 dialog 元素。
  按钮  关闭测试对话框
  ```
  —— **与本项目抽屉的模式完全相同**（念名字、不念角色词）。
- **判定**：抽屉的对话框语义**已正确暴露**，NVDA 对它的处理**与标准参照 ARIA dialog 等价**。
  「NVDA 是否念出『对话框』」属 NVDA 自身行为（对比：原生 Windows 对话框——如系统防火墙
  提示——NVDA **会**念「对话框」）。**不作为本项目缺陷**，但因此**不能声称「NVDA 会念出对话框」**。

### 4.2 抽屉关闭按钮未捕获到

- DOM 证据：导出抽屉的关闭按钮为 `<button aria-label="关闭">`（`ExportDrawer.tsx:140`），
  首次 Tab 即落于其上（`activeElement` = `<BUTTON aria-label="关闭">`）。
- 但**多次运行均未拿到该按钮的 NVDA 播报**（该时段机器被其它程序抢占前台）。
- **如实标注：未验证**，不推断其播报内容。

### 4.3 工程问题（非应用缺陷）

- `nvda.exe` 启动器受**残留单实例互斥量**影响会静默退出；须用 `nvda_noUIAccess.exe`。
- add-on `manifest.ini` 的 `description` **含逗号会被解析成 list → 静默不加载**。
- 中文 argv 经控制台代码页会**损坏**，窗口匹配必须用 ASCII 标记。
- **捕获依赖浏览器持有 OS 前台**；共享机器上他人操作会抢占前台，导致部分片段丢失。

## 6. 遗留风险

- **读屏行为依 NVDA 版本/配置而异**：换 NVDA 版本或语音/详细度设置，播报文本会变；
  本结论锚定「NVDA 2026.2 + 中文 + 默认详细度」。
- **Chromium 无障碍树需读屏在场**：本次用 `--force-renderer-accessibility` 强制开启；
  真实用户环境由 NVDA 的存在自动触发，一般一致，但未逐项复核。
- **「对话框」角色词**：若产品/验收方要求读屏**明确念出「对话框」**，需另行确认 NVDA 侧设置或
  改用其他机制（如原生 `<dialog>` 元素），**本轮未验证能否达成**。
- **捕获脚本依赖前台**：作为回归工具时，必须在**无他人抢占前台**的机器/时段运行，否则结果不可用。
- **未覆盖回归**：本轮是**一次性实测**；`nvda_sr_verify*.mjs` 可作为回归脚本，但**未纳入 CI**
  （CI 无交互式桌面，无法跑真实 NVDA）。
