## 突破：不装 MathType 也能转换（用户确认「没有」授权后）

- 用户确认**团队没有 MathType 授权** → 「保持对象」路线不可行，必须转换。
- **找到并实测打通了无需 MathType 的转换链路**：MathType OLE 对象内含 `Equation Native` 流（MTEF 二进制），用 `olefile` 取出、跳过 28 字节头，用开源 **mtef-py**（Apache-2.0，零外部依赖）解析成 LaTeX。**这是精确解码，不是 OCR。**
- **成功率 99.69%**：单个真实学科网文件（`专项06 浮力的计算和实验专题（解析版）.docx`）980 个公式 → 977 成功、3 失败，耗时 **0.21 秒**。
- **端到端验证通过**：MTEF → LaTeX → OMML，8/8 在 **Microsoft Word 与 WPS 中均渲染为原生可编辑公式**。渲染目视确认：`F_B浮=G−F示=4N−3.6N=0.4N`、`F浮=F2=ρ水gV苹果`、`V=F2/(ρ水g)`、`kg/m³` 等，分式/上下标/希腊字母/中文下标全部正确。
- **踩坑记录**：MTEF 输出的中文是 `{\text{[U+6d6e]}}` 形式，替换时**必须替换在已有 `\text{}` 内部**；若再套一层变成 `\text{\text{浮}}`，渲染器会直接报错 `ToCommands returned empty`。另外 MathType 会在部分公式开头产生 `~` 占位符，需去掉。
- **项目结论修正**：旧式公式**不再是阻塞项**；唯一仍需人工介入的只剩扫描 PDF。
- 新增脚本：`.workbuddy-ai/mtef_test.py`、`mtef_corpus_test.py`、`mtef_roundtrip.py`；证据：`outputs/validation_30/mtef_conversion_test.json`、`mtef_corpus_test.json`、`mtef_roundtrip.json`、`mtef_roundtrip.docx`、`mtef_roundtrip_preview.png`。报告新增第 9 节，全文 599 行。

## 【踩坑·必记】`.bat` 无法启动的真实原因（2026-10-07）

用户报「无法启动 bat 文件」。应用本身完全正常（`python -m webui` 直接跑能起服务、浏览器能加载），问题在 `.bat` 文件本身，**两个叠加的原因**：

1. **换行符是 LF 而非 CRLF**（主因）。用 Write/heredoc 生成的文件是 LF 换行，而 **Windows cmd.exe 需要 CRLF**——LF 会让多行括号块（`if not defined PY ( ... )`）解析失败，脚本一闪即退或报语法错误。实测 `CRLF=0, LFonly=42`。
2. **路径反斜杠被 Git Bash 转成正斜杠**。通过 bash heredoc 写文件时，`C:\\Users\\...` 被 MSYS 路径转换改成了 `C://Users//SOAP//...`（双斜杠），cmd 无法识别。

**修法**：① 用 **Write 工具**直接写文件（不经 bash，反斜杠不被转换）；② 再用 Python 把 LF 批量转 CRLF（`raw.replace(CRLF, LF).replace(LF, CRLF)`，用 `bytes([13,10])` 表达避免反斜杠再次被转义）；③ **避免多行括号块**——改用单行 `if not defined PY set "PY=..."` 形式，最稳。
**验证方式**：`cmd //c "启动题库.bat"` 实测，确认服务器起来 + 浏览器加载（日志见 `GET /api/search 200`）。
**通用教训**：**给 Windows 用户生成的任何 `.bat`/`.cmd` 必须用 CRLF 换行**；且**不要通过 bash 传递含反斜杠的路径字面量**。项目里已扫过，仅此一个脚本文件。

## E1 探针：前端 A4 近似分页可行性（2026-10-07，已完成，结论「可行」）

交付 `outputs/webui/E1-前端分页可行性验证.md`（v2，240 行）+ 独立原型 `spike/a4-preview/`（未接入 frontend）。

- **结论：可行**，推荐**路线 B（JS 测量 + 手动分页）**。路线 A（CSS `column`+`break-inside:avoid`）实测能跑但**"简单"是假象**——栏数仍要 JS 反推、做不到逐页页头页脚。
- **【关键发现·我已独立实测证实】Word 的「1.5 倍行距」≠ CSS `line-height:1.5`**。Word 是「1.5 × **字体自然行高**」：宋体 12pt 自然行高≈15.6pt → **实测真实 PDF 正文行距中位数 23.4pt**，而 CSS 认为 18pt，**低估 1.30 倍**。这正是探针页数对不上的主因。修法：引入 `WORD_SINGLE_LINE_FACTOR = 1.29`。
- **修正后：考试/测验/作业三模板「学生版」页数与真实 A4 全部相等（6=6、6=6、4=4），且逐页起始题号 100% 一致**。答案解析版差 1 页，根因是**第 3 题单题高度 1048.7px > 页高 930.5px**——真实 Word 把该题**拆两页**，探针坚持「整题不拆」独占一页。**这是「不截断」与「页数精确」的天然冲突，非 bug。**
- **两个真实技术坑**：① **`transform:scale()` 污染测量**——`getBoundingClientRect()` 返回变换后尺寸（实测导致同配置页数 5→3），测量层必须放在 transform 容器之外；② 图片不预置 width/height → 加载后回流必乱。解法：后端 `fit_image_size` 是**纯函数**（原始像素+可用宽→显示尺寸），前端搬规则并在 `<img>` **预写尺寸**。
- **性能**：每次重算 **0.02–0.08ms**（50 题仍 <0.1ms），比 200–300ms 防抖预算**快三个数量级**。
- **成本**：核心引擎约 850 行、生产组件预计 600–900 行，**不需要新依赖**；不新增页面/端点。

- **"跳转网页"根因核实**：站内导航**不新开标签**（HashRouter，全项目 grep 无 `window.open`/`target="_blank"`）→ 痛点是**启动两次跳转（黑窗 cmd→弹浏览器）+ 浏览器外壳的网页感 + 关闭即消失**，**不是"点一下跳一次"**。
- **A 技术选型**：主线 **pywebview（系统 WebView2）作第三个外壳** `editions/desktop/`（外壳层仅 +3–8MB，与 Python 后端同进程）；过渡态 **无黑窗静默启动 + 浏览器 `--app` 去地址栏**（0 改动）；**否决 Electron**（100–150MB/200–300MB 内存/3–6s 冷启动，违背轻量化前提）。**Mac/Linux 不做**（导出硬依赖 Windows COM）。
- **持久化**：SQLite 不变；客户端 UX 状态放**独立 `outputs/webui/client_state.db`**（不污染交付库）；**门禁 `previewFresh` 继续不持久化**，只加**只读足迹**（`{paperId,lastPreviewedAt,contentDigest,settingsKey,app_version,editor_sdk_version}`，**不参与 `isExportUnlocked` → 篡改也解锁不了，不可绕过**）。**否决 PM 的 Q3「显式确认替代重新预览」**（contentDigest 相同不担保渲染相同；削弱误操作保护）。
- **打包**：PyInstaller onedir（解压 ≈100–112MB）+ Inno Setup → **压缩包 ≈30–45MB**；**≤50MB 可达但紧，建议硬指标 ≤60MB**；**含 64MB `bank.db` 则 ≤50MB 不可能** → **bank.db 独立分发（首启导入）**。升级用**绿色版覆盖**（离线友好）。接入用 `editions/desktop/` + **新增 `QB_SHELL`**（browser|webview），**不新增 `QB_EDITION=desktop`**（语义==local）。
- **工作量**：S1 过渡态 2–3 / S2 WebView 外壳 8–12 / S3 打包 8–12 / S4 持久化交互 6–9 ≈ **24–36 人日**（每步可独立交付可回退）。
- **风险**：**R1 最高 = `editor_sdk` 是仓库外本地 MCP 服务（39099 起），导出硬依赖它+Word/WPS**——是否随包分发并拉起？无答案（Q-A）。R2 体积阈值 vs 64MB 数据。R3 PyInstaller×pywin32(COM)×pystray×uvicorn 打包坑**单元测试测不出** → 建议先做**打包探针 spike**。
