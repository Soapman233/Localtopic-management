# T5 多人部署方案比较（架构建议，不实施）

推荐短期继续每人本地库、共享导出文件；当团队确需共同编辑一个题库时，再建设集中服务。不能直接把 `bank.db` 放共享盘，也不能只把监听地址改成 `0.0.0.0` 就宣布支持多人。

SQLite 官方说明网络文件系统的同步与锁可能不可靠；可选路线是客户端/服务端数据库，或数据库与访问进程都在同一台主机、远端仅通过 API 访问。[SQLite 网络访问说明](https://www.sqlite.org/useovernet.html) 因而“10 人”本身不是必须迁移 PostgreSQL 的充分理由，编辑并发、权限、运维和统一数据需求才是选择依据。

| 方案 | 成本 | 优点 | 风险／限制 |
|---|---|---|---|
| 短期：单人本机 SQLite，每人独立副本，只共享 DOCX/PDF | 约 0.5–1 人日制定发版、备份与归档规则；通常无需新增服务器 | 复用当前软件和 Office，离线可用，故障隔离 | 副本会分叉；不自动合并数据库，团队不能实时共编 |
| 过渡：集中 API，SQLite 留在服务端本地磁盘，串行写入 | 在认证、权限、审计和导出队列齐备的前提下，约 10–20 人日；需专用主机和维护 | 数据集中、改造较小，可验证真实并发负载 | 单写者吞吐和长事务；服务/主机单点；并非把原库共享挂载给客户端 |
| 中期：集中 API + PostgreSQL + 用户/权限/审计 + 受控文件存储 | 约 20–35 人日开发迁移，另 5–10 人日试点与验收；持续承担主机、存储、备份与运维 | 支持集中协作、事务并发和权限扩展，后续可扩容 | 数据库适配、检索等价性、权限缺口、Office 导出服务成为新瓶颈 |

估算假设：现有约 8 千题、10 名用户、单一教研团队，无外部身份平台集成和复杂跨组织隔离；这是待原型验证的工作量，不是报价或交付日期。没有为本轮购买资源、开放端口、安装数据库或迁移数据。

短期建议指定一个维护者保管主库和已核验备份，按版本分发只读种子包；使用者只在本地副本组卷和导出。需要回流题目修订时提交有来源的修订清单，由维护者逐项审核，不能覆盖整库或直接拼接多个 SQLite 文件。分发源 DOCX 与媒体时附完整性清单，避免别人收到数据库却无法打开原机桌面路径下的公式预览图。

中期的最小完整边界：

1. 浏览器 → HTTPS/API → 数据库；所有业务入口鉴权。阅读者可检索/组卷/导出，编辑者可修改题目/元数据和提交复核，管理员负责用户、备份、恢复与迁移。学校/团队边界要先定，不能仅隐藏按钮当权限。
2. 对题目和试卷写入实行版本前置条件，冲突返回可理解的 409，禁止后写覆盖先写；保留旧版、锁定试卷快照与审计事件（谁、何时、何对象、前后版本、原因）。审计与业务写入同事务；权限可用应用层实现，PostgreSQL 行级策略是后续加强手段，不能替代 API 身份校验。[PostgreSQL 行安全文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
3. 源 DOCX、媒体和导出件使用服务端受控存储键与 SHA256，不依赖每位教师的绝对路径；上传去重、来源追踪、受控下载和备份恢复覆盖数据库与文件。保留原始公式字节及预览图，不能丢失本轮查明的源图/OLE 冲突证据。
4. 导出是独立任务队列：记录版本、模板、答案模式和内容指纹，限制并发，失败可重试且不混用不同用户的中间文件。现有 editor_sdk 与 Word/WPS 是本地 Windows 依赖，不能假设搬到普通 Linux 主机即可运行；先验证专用 Windows 导出工作机的无人值守能力和使用许可，仍需双端实测。
5. 备份、恢复演练、访问日志、任务失败监控与升级回滚有明确维护责任。服务端 SQLite 如作过渡，也必须通过 API 访问本机文件，不能跨网络挂载数据库。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

迁移顺序：先确认角色、共享范围与同时编辑负载；在副本上搭建 API/认证/导出原型；移除路径依赖并迁移源文件；再适配数据库。保留原 id、题目版本、来源 SHA、公式复核状态和试卷快照，或建立可审计的旧新 id 映射。SQLite 专属 FTS、`rowid`/自增、PRAGMA、SQL 占位符和事务行为需逐处适配；检索沿用现有中文分词结果先做结果集一致性对照，不能宣称换库后天然等价。

正式切换前：核验备份；只在迁移副本校验核心表行数、外键、完整快照、标签及复核状态、抽样内容哈希和媒体可用性；用至少 10 个会话演练检索、并发改同题、组卷和排队导出，记录延迟与冲突结果。安排短暂只读窗口做最终增量迁移并验收；保留旧库只读回滚点。上线后新写入如何回滚必须事先定义，不能用旧库恢复直接丢掉新编辑。无需重跑 `outputs/preprocess_final/`。

开始实施前需人工决定共享主库还是独立副本、部署位置、身份来源、维护者和预算；本轮仅提供可审阅的方案，没有执行上述架构变更。
