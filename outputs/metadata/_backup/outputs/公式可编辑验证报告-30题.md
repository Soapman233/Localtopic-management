## 1. 结论速览（TL;DR）

| 路径 | 定义 | 10题结果 | 能否满足“导出公式可编辑” |
|---|---|---|---|
| **A** | 源文件已是 Word 原生公式（OMML） | **10/10 通过** | ✅ 可以 |
| **B** | 源文件为旧式公式对象（OLE，MathType） | **0/10 通过** | ❌ 当前环境不可自动转换 |
| **C** | 源文件为扫描 PDF，需识别重建 | **9/10 通过**，1题不适用 | ⚠️ 可以，但需人工校对（非全自动） |

**跨客户端实测（新增）**：原生公式（OMML）在 **Microsoft Word 10/10 通过**、**WPS 10/10 通过**；MathType 对象在两个客户端中**都无法编辑**。

**关于学科网的技术路线（新增）**：经直接检查你手上的下载文件，**学科网下载的 Word 文件压倒性使用 MathType**（学科网目录内 `Equation.DSMT4` 达 11,845 个，99/209 份文件只有旧式对象、无原生公式）。但**照搬他们的输出格式会违背你的兼容性要求**——建议复现他们的「文本存储 + 导出时渲染」架构，把渲染目标换成 OMML。详见第 7 节。

**能否保持 MathType 对象（新增）**：**能，且完全无损**——实测 980 个对象往返后嵌入数据**逐字节一致**、显示正常、零转换成本。**代价是编辑必须装 MathType**。推荐做法是「原件归档 + 题库存 LaTeX 文本 + 导出时按需渲染」，两者兼得。详见第 8 节。

**突破：旧式公式不再是阻塞项（新增）**：既然团队没有 MathType 授权，就需要转换。实测证明**不装 MathType 也能转**——用开源 MTEF 解析器（Apache-2.0）直接解码公式二进制，**成功率 99.69%（977/980）**，980 个公式耗时 0.21 秒；转换结果已在 Word 与 WPS 中双双渲染为原生可编辑公式。详见第 9 节。

**阶段 1 预处理管线已实现（新增）**：按技术路线落地的 `pipeline/` 已可运行——把 DOCX 转成「结构化题目 + LaTeX 公式 + 图片 + 来源定位」。批量实测 40 份文件 **40/40 成功、1,698 道题、公式转换率 97.09%**。全量格式覆盖率：**MathType 占旧式对象的 98.48%，可自动转换；约 1.06% 的其他格式需人工处理**。详见第 10 节。

**一句话**：只要公式是 Word 原生公式，整条“提取 → 组卷 → 导出 → 编辑保存”链路在 WPS 与 Word 上都已经跑通；真正的瓶颈是**旧式 MathType 对象无法在本环境自动转成原生公式**，以及**扫描 PDF 必须人工校对**。

## 3. 三条路径的定义与对比维度

### 3.1 路径定义

| 路径 | 源数据形态 | 目标 | 关键动作 |
|---|---|---|---|
| **A** | DOCX 内含 OMML（`m:oMath`） | 保留并重组为可编辑公式 | 按题号裁取范围 → 复制到新文档 → 导出 |
| **B** | DOCX 内含 OLE 对象（`o:OLEObject`，如 `Equation.DSMT4` / `Equation.KSEE3`） | 转换为 OMML | 需专用转换器或重建 |
| **C** | PDF（无文本层，仅水印） | 识别文字 + 重建公式为 OMML | 页面渲染 → 视觉识别 → 结构化重建 |

### 3.2 对比维度（逐题记录）

| 维度 | 含义 | 判定方式 |
|---|---|---|
| 提取完整性 | 题干/选项/图表是否完整 | 与源文本逐字比对 |
| 公式结构 | 公式是否以原生结构保存 | 统计 OMML / OLE 节点数 |
| 公式数量一致性 | 提取前后公式数是否一致 | 源 vs 导出 |
| WPS 可编辑性 | 能否改到公式内部的具体字符 | 逐个公式改一个字符 |
| 保存重开保持 | 修改后保存、重开是否仍在 | 保存 → 关闭 → 重开 → 比对 |
| 图表保留 | 电路图/滑轮图等是否保留 | 统计媒体文件数 |
| 内容正确性 | 公式语义是否正确 | 检查未知字符、变量错位 |
| 自动化程度 | 自动 / 需人工辅助 | 明确区分，不混淆 |

> **判定口径（重要）**：结构上“有 OMML 节点”**不等于**“在 WPS 中可编辑且能保存”。两者分开记录。同样，“人工辅助重建”**不计入**“自动转换成功”。

### 7.4 建议复现的技术路线

学科网路线的**本质**是「**公式以文本存储、导出时再渲染**」，这一点非常值得照搬：

```text
学科网路线（架构）
  LaTeX 文本存储  →  导出时由引擎渲染  →  Word 中的公式对象
                     ↑ 照搬这一段
                                     ↑ 但把渲染目标从 MathType 换成 OMML

我们的路线
  LaTeX 文本存储（数据库里存公式源码，可检索、可复用、可版本化）
        ↓ 导出时渲染
  OMML（Word 原生公式）—— WPS 与 Microsoft Word 都能直接编辑
        ↓
  DOCX（可编辑公式） + PDF（打印对照）
```

具体做法：

1. **入库时统一转成 LaTeX 文本**（或等价的结构化表示）存库，不把公式留成 OLE 对象。
   - 原生 OMML → 转 LaTeX：可程序化完成。
   - MathType OLE → LaTeX：需要转换器（MathType 自带批量转换，或第三方），**这是必须先攻克的环节**。
   - 扫描 PDF → LaTeX：视觉识别 + 人工校对。
2. **导出时用 LaTeX → OMML 渲染**，生成 Word 原生公式。
   - 本报告已实测该链路可行：C 组 10 题就是用 LaTeX 现场渲染成 OMML，且在 WPS 中可编辑。
3. **导出同时生成 PDF** 作为打印对照，PDF 里的公式不需要可编辑。
4. **不引入 MathType 依赖**，避免每台机器都要商业授权，也避免版本差异。

### 7.5 关于「版本不一定一致」

你提到团队 WPS 版本不统一。这对本方案是**有利**的：OMML 是 Office 标准格式，WPS 各版本对它的支持远好于对 MathType 对象的支持。但仍建议：

## 9. 突破：不装 MathType 也能转换（已实测打通）

> 这一节推翻了前面「旧式公式是阻塞项」的结论。**阻塞已经解除。**

### 9.1 原理

MathType 公式虽然以 OLE 对象存在，但对象内部有一个 `Equation Native` 流，存的是 **MTEF**（MathType Equation Format）二进制数据。**这个格式可以被程序直接解析**，不需要 MathType 参与：

```text
DOCX 里的 OLE 对象
   └─ Equation Native 流（MTEF 二进制）
          │ 用 olefile 取出，跳过 28 字节头
          ↓
      MTEF 解析器（开源，Apache-2.0）
          ↓
        LaTeX 文本
          ↓ 导出时渲染
      OMML（Word/WPS 原生可编辑公式）
```

**这是精确解码，不是 OCR** —— 公式结构（分式、上下标、根号、希腊字母）是从二进制里直接读出来的。

### 9.2 实测结果

**转换成功率**（单个真实学科网文件，`专项06 浮力的计算和实验专题（解析版）.docx`）：

| 指标 | 结果 |
|---|---|
| 扫描公式对象 | 980 |
| 成功转换 | **977** |
| 失败 | 3 |
| **成功率** | **99.69%** |
| 耗时 | **0.21 秒 / 980 个** |

**端到端验证**（从真实 MathType 对象一路到可编辑公式）：

| 环节 | 结果 |
|---|---|
| MTEF → LaTeX | 8/8 正确 |
| LaTeX → OMML 渲染 | 8/8 成功 |
| 在 Microsoft Word 中打开 | **8 个原生公式** |
| 在 WPS 中打开 | **8 个原生公式** |
| MathType 是否安装 | **否** |

实际转出的公式（两端渲染结果一致）：

| 原始公式含义 | 转换结果 |
|---|---|
| 阿基米德原理 | `F浮=F2=ρ水·g·V苹果` |
| 浮力计算 | `FB浮=G−F示=4N−3.6N=0.4N` |
| 密度公式 | `V=F2/(ρ水·g)` |
| 质量公式 | `m=G苹果/g=F1/g` |
| 单位 | `kg/m³` |

**下标、分式、希腊字母 ρ 全部正确还原，中文下标也正常显示。**

| 约 80% 的旧式公式 | ❌ 阻塞项，需买 MathType 或人工重建 | ✅ **可自动转换，成功率 99.7%** |

## 10. 阶段 1 预处理管线（已实现并验证）

按技术路线推进的第一阶段已经落地为可运行的代码，位于项目 `pipeline/` 目录。

### 10.1 它做什么

把真实试卷 DOCX 转成**结构化题目 + LaTeX 公式 + 图片 + 来源定位**：

```text
DOCX ─┬─ 原生公式（OMML）──────────→ LaTeX
      ├─ MathType 对象（MTEF 二进制）→ LaTeX   ← 无需安装 MathType
      └─ 图片 / 表格 / 段落 ─────────→ 结构化文本（公式位置用 ⟦Fn⟧ 占位）
                                          ↓
                     题目切分：每题带自己的公式 ID、图片、来源段号
                                          ↓
              输出：<名>.scan.json + <名>.questions.json + _summary.json
```

**后续阶段不再需要解析 DOCX。**

### 10.2 文件构成

| 文件 | 职责 |
|---|---|
| `pipeline/omml.py` | OMML → LaTeX（分式、上下标、根号、n 元运算、定界符、矩阵、重音、极限等） |
| `pipeline/mtef_conv.py` | MTEF → LaTeX，**带超时隔离**（二分定位坏公式） |
| `pipeline/docx_scan.py` | 扫描 DOCX：正文顺序、公式、图片、OLE 流提取 |
| `pipeline/segment.py` | 按题号切分题目（子题不拆） |
| `pipeline/stage1.py` | 命令行入口 |
| `pipeline/vendor/mtef_py/` | 内置 MTEF 解析器（Apache-2.0，含 LICENSE 与 NOTICE） |
| `pipeline/README.md` | 使用说明 |

### 10.3 格式覆盖率（决定自动化的天花板）

对全部 567 份 DOCX 里的 54,663 个旧式公式对象统计：

| 格式 | 数量 | 占比 | 本管线支持 |
|---|---:|---:|---|
| `Equation.DSMT4`（MathType） | 53,832 | **98.48%** | ✅ 支持（实测 17,933/17,946 = 99.93%） |
| `Equation.KSEE3`（WPS 公式 3.0） | 491 | 0.90% | ❌ 不支持，**且会让解析器死循环** |
| `DSEquations` | 246 | 0.45% | ⚠️ 未验证 |
| `Equation.3`（微软旧公式编辑器） | 90 | 0.16% | ❌ 不支持 |
| `AxGlyph.Document` | 4 | 0.01% | 非公式（绘图对象） |

**结论：98.48% 的旧式公式可以自动转换；约 1.06% 需要人工处理。**

> 这是一个重要修正：之前把「旧式对象」当成一类，实际上里面混了至少三种互不兼容的格式。**只有 MathType（DSMT4）是主流，也只有它被开源解析器覆盖。**

### 10.5 开发中发现并修复的四个真实缺陷

| 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|
| **传错数据** | 168 个公式全部返回 EMPTY，成功率 0% | 把整个 OLE 容器文件（3584 字节）当成 MTEF 数据传给解析器，而不是先取出内部的 `Equation Native` 流（约 296 字节）。**解析器不报错，只静默返回空** | 增加 `_equation_native()` 提取流 |
| **命名空间缺花括号** | 17/40 文件直接抛 `SyntaxError: prefix 'urn' not found` | `V = "urn:schemas-microsoft-com:vml"` 少了 `{}`，被当成 XPath 前缀 | 常量改为带花括号 |
| **解析器死循环** | 全量跑到第 106 份文件后**永久卡住**（10 分钟无进展，此前 17 分钟也没跑完） | `Equation.KSEE3`（WPS 公式 3.0）的二进制布局解析器不认识，会**无限循环**而不是报错。全库有 491 个这种对象，每个耗一次超时 | 按 ProgID 预判，对已知不支持的格式**直接跳过、不送去解析** |
| **进程创建开销** | 40 份文件要 2.17 秒，单条模式要 72 秒 | 每处理一块就新建一个进程池，而每次 spawn 约 0.43 秒 | 改为**流式工作进程**：一个进程顺序处理、逐条回报结果；卡住就重启并从下一条继续（不再二分） |

> 第 1 和第 3 个缺陷尤其值得记：**静默返回空值、以及死循环，都比抛异常更危险**。只看「跑通了」会把它们误判成资料问题或性能问题。
>
> 修复后全量耗时从「10 分钟跑不完」降到 **65 秒**。

### 10.6 设计要点

1. **公式统一成 LaTeX** —— 三种来源汇成一种表示，题库可检索、界面可渲染、导出可转 OMML。
2. **占位符保序** —— 正文里公式位置写 `⟦Fn⟧`，切分和重组时公式不会串位。
3. **超时隔离** —— MTEF 解析器在极少数畸形公式上会死循环（实测遇到过一次）。整批在独立进程跑并设截止时间，超时后二分定位，**把一条坏公式隔离成一条 TIMEOUT，而不是拖垮整份文件**。
4. **失败进队列，绝不静默丢弃** —— 任何非 `OK` 的公式都带 `needs_review` 和预览图。
5. **只读源文件** —— 全程不修改输入。

### 10.7 使用方式

```bash
# 单文件
"$PY" -m pipeline.stage1 "试卷.docx" --out outputs/preprocess

# 整目录
"$PY" -m pipeline.stage1 "D:/资料目录" --limit 40 --timeout 8

# 安静模式
"$PY" -m pipeline.stage1 "D:/资料目录" --quiet
```

### 10.8 本阶段仍未覆盖

- ❌ **扫描 PDF**（C 路径）不在本管线内，需要识别 + 人工校对，单独处理。
- ❌ **KSEE3 / Equation.3 / DSEquations** 三种格式（约 1.5%）暂不支持，进人工队列。
- ❌ **题目切分基于题号正则**，对编号不规范的资料需要人工校正（切分结果保留段号可回溯）。
- ❌ 本阶段**不产出可编辑 DOCX** —— 那是导出阶段（LaTeX → OMML）的职责。
