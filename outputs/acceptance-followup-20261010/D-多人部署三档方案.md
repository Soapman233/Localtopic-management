# 任务 D：多人部署三档方案（仅评估）

建议短期每人本地副本、共享导出文件；共同维护同一题库成为明确需求后，再做中期集中服务。完整多租户适用于多个独立团队，当前不建议一步建设。

本次从 `create_app()` 实际注册路由导出清单：**47 个业务端点 + 1 个健康端点 = 48 个 API 端点**。任务中的 47 与 PROJECT 中的 48 是统计口径不同；下表覆盖全部 47 个业务端点，完整 method/path 见 [端点清单](<D:/Open-source project/Localtopic-management/outputs/acceptance-followup-20261010/D-端点清单.json>)。

工作量假设：当前约 8 千题、单团队约 10 名教师、无复杂采购/计费/SSO 集成；估算来自现有代码依赖与改造范围，尚无并发原型计时，不是报价。持续费用需要按并发、存储增长、恢复目标与运维能力选型后询价，本文未引用未经核实的云价格，也未购买、部署或迁移。

SQLite 官方说明网络文件系统的同步、锁行为可能导致损坏；数据库文件与执行数据库操作的进程应同机，远端通过 API 访问，或采用客户端/服务端数据库。[SQLite 网络使用说明](https://www.sqlite.org/useovernet.html) 因此禁止让多人直接打开共享盘上的同一 `bank.db`。低写并发时，“集中 API + 服务器本地磁盘 SQLite”可以作为中期过渡，需鉴权、审计、单写者与负载实测，约 10–20 人日改造并另做试点；不能仅改监听地址或启用 WAL 就算多人版。当前项目保持 DELETE journal 的约定，本轮不改。[SQLite 服务端适用场景](https://www.sqlite.org/whentouse.html)

## 中期最小完整设计

浏览者可检索、建自己的卷和导出；编辑者可修题/来源/人工难度；复核者可决策公式与知识点；管理员管成员、恢复及平台配置。试卷共享权另按卷主/协作者判断，不把“阅读题库”自动扩展为“修改任何人的卷”。身份由服务端校验的会话/令牌提供，异地访问优先受控 VPN 或 HTTPS 网关，数据库端口不向教师开放；身份到期、权限变更和文件下载同样验证。

目前应用级 Python `RLock` 仅保护同进程写入，多进程/多工作机不能依赖它保证全局串行。并发改同题/同卷需要乐观版本校验和事务约束；审计写入与业务变更同事务，记录用户、时间、对象、动作、前后版本和原因。拒绝的操作记录安全日志；检索浏览不必逐次复制完整题干入审计。恢复与删除政策须能支持误操作追溯。

迁移到 PostgreSQL 需处理 SQLite PRAGMA、占位符、自增/rowid、事务锁、FTS5 及中文检索；先保留原分词结果并做结果集/排序/缺失桶计数对照，不能声称换库天然等价。源 DOCX、预览图、公式源字节与导出件转为服务器受控路径或对象存储键，保留 SHA256 与来源，解决数据库中原机桌面绝对路径依赖。

现有 Word/WPS、editor_sdk 是本机 Windows 依赖。建议先用单独 Windows 工作机验证真实导出、超时、失败重试和无人值守条件；队列作业绑定试卷内容版本、模板、答案模式与输出指纹。不能假设直接迁到 Linux 即可保持公式可编辑性与分页。本轮没有安装服务或改端口。

## 长期租户隔离选择与迁移

至少比较“共享库 + tenant_id + 行安全”“每租户独立 schema”“每租户独立库”。建议先用共享 PostgreSQL 库和明确租户外键/唯一约束评估，数据隔离要求较高的客户再评估专库。共享库可用 RLS 加强隔离，但表所有者、超级用户及具有 BYPASSRLS 权限的角色可能绕过策略；运行账号与策略必须专门配置验证，不能只加一条 policy 就宣称隔离完成。[PostgreSQL 行安全说明](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

租户身份来自已验证成员关系；不信任客户端任意传入的 tenant_id。题目、来源、公式、标签、版本、试卷、快照、审计、作业与文件归属都要闭合；复合外键防止跨租户关联，唯一键按所选共享规则重新设计。缓存、日志、预览文件及后台导出同样携带租户，撤销成员权限后仍不能凭旧 job_id/preview key 下载。租户迁移或停用需处理正在执行作业、共享资产、恢复和保留规则；不要向“完整多租户”附带未经需求确认的计费系统。

## 可审阅的迁移与退出步骤

1. 确认目标是独立副本还是同库共编，以及同时写入人数、管理员、异地范围、备份恢复目标和预算。短期不得把多个本地 SQLite 直接覆盖合并。
2. 原库备份并 `verify_backup(原库, 备份)`；只在副本建立中期原型，先验证身份/对象权限、受控文件和 Windows 导出链路，再决定 PostgreSQL 或服务器本地 SQLite 过渡。
3. 迁移脚本采用版本化、可重跑且可审计的步骤；保留原 id 或记录映射。逐表核验行数、外键、公式原始值与复核状态、题目版本、锁定快照、媒体哈希；不重新生成预处理产物。
4. 针对 47 个业务端点逐一跑允许/拒绝矩阵；两个用户改同题、改同卷须出现可解释冲突而非后写覆盖；十会话负载与队列导出记录延迟/失败。长期增加两个租户的交叉 ID、嵌套对象、批量请求、统计、预览缓存及下载越权测试。
5. 正式切换设置短暂只读窗口，停旧写入、做增量核验后开新服务；保留原库只读回滚点。开写之后回滚要保留新写入事件并安排重放/导回，不能直接恢复旧库丢掉新修改。数据库与文件必须一起演练恢复，并指定维护人。

本任务只形成选型与迁移方案；没有部署、开放公网访问、采购或改动数据库/端点实现。三档选择、预算、身份来源及隔离等级留待人工决策。`python -m unittest discover -s tests` 实测 311 项：310 通过、1 跳过，27.522s；全量回归日志见 `.qa_acceptance_20261010/D-tests.log`。
