### D. 风险层

**10. A 自称最大风险（P-05：写交付库 + 复用 `stage1` 未探针）→ 部分认同，并补充 A 未看到的风险**

认同 P-05 是最大 P0 风险。但 A 漏看了：

- **(a) 幂等重导不更新归属**：A 定义重复文件返回 `skipped=true`（E1 载荷）。若同一 DOCX 由**不同教师**再次导入，`skipped=true` 后 `owner` **不会被更新** → 归属错记给首导者。A 未定义此分支。
- **(b) "考查"口径初始为空集**：P-03 把"考查口径"定义为 `question_labels.review_status='已确认'`（A `:180`）。但库里 **38,588 条关联 100% 是"待复核"、已确认 = 0** → **"按考查检索"上线即返回空**。A 的 T-03V 只做"抽样 50 题对照"，未处理"初始不可用"。P-02 的批量确认是其前置。
- **(c) Web 导入直接写交付库**：A 反复强调"开发/测试用副本"，但 P-05 是**给教师用的功能**——每个教师每次导入都**写交付库**（`outputs/bank.db` 即生产库）。这已超出"验证用副本"的语境，属**运行期写生产数据**，A 未评估"坏导入污染交付库"的恢复路径。
- **(d) 单 worker 争用**：导入与预览/导出共用 `JobManager` 单后台线程 → 一次导入会阻塞预览/导出。A 标"可接受"，但未给出"导入大文件时长的上界"（阶段1 实测 ~0.32s/文件，但含公式的复杂文件可能显著更慢）。

**11. 被整条链漏掉的内容 → 有 3 处**

- **(i) 报告"命题工作程序（含制订双向细目表）"标注为强实证（官方文件）**（报告 `:166` 表），R1 的 33 条主张**无一条对应**；最接近的 C29（命题意图/考点映射）却是"理论推断"→ P 归入"不投入"。**一个强实证的报告要素被折叠进理论推断条目而落空。**

## 六、对两个待拍板项的独立意见

### 待拍板项 1：`bank/query.py` 新增筛选键授权

**A 的提案**：授权在 `bank/query.py` 新增 `cognitive_level`/`content_domain` 两个可选筛选键，"不得改动现有查询计划与 CAST 位置"。

**我的独立核查（读 `bank/query.py`）**：
- 筛选分发**不是**"新增函数即可"，而是硬编码在**既有函数 `_build_where`** 内：
  - `_QUESTION_FILTERS` 字典（`query.py:30-36`）**列出**键，但循环体内又用**内联字面量字典**再取一次值（`query.py:61-66`）：`val = {"chapter": chapter, "qtype": qtype, ...}[name]`。
  - 要加两个筛选键，D **必须**同时改：`_build_where` 签名 + 内联字典 + `_QUESTION_FILTERS` + `search_full`/`search` 签名 + `webui/services/search.py`。**这已修改多个既有函数**，与 `AGENTS.md §6.3.3`"`bank/query.py` **只允许新增函数**"直接冲突。
- 该区域正是 AGENTS §7.3 反复警示的 **FTS `CAST` 位置敏感区**——历史上改 join 曾导致 `SCAN q`（818 命中 ≈ 6.9s）。

**结论**：**同意授权，但 A 的措辞不充分，需收紧为——**
1. 明确授权范围是"**新增一个函数**（如 `search_with_taxonomy()`），**不得修改 `_build_where` / `search` / `search_full` 的函数体**"；若确需改既有函数，须在冻结清单中**逐函数列名**，并**同时**要求"结果集与等价 SQL 逐条一致"（T-03b 已有）**加上**"与改动前 `search_full` 在旧参数下结果逐条一致"的回归项。
2. 明确**未定义行为防护**：`cognitive_level`/`content_domain` 为**可空且自由文本**（P-03 不做枚举校验），筛选用 `=` 精确匹配 → 用户输入不匹配时**静默返回空**（非报错）。A 应在验收里写清"空结果 vs 报错"的预期，否则易被当成 bug。

### 待拍板项 2：`settings.default_owner` 验收口径

**A 的提案**：新增 `settings.default_owner`；P-09 验收 #1 要求字段"非'待补充'"；A 自己指出"若未配置，新导入仍可能为空"，需明确口径。

**我的独立核查（读 `bank/db.py`）**：
- `papers.created_by TEXT NOT NULL DEFAULT '待补充'`（**NOT NULL**）；`source_files`/`questions` 拟新增列为 **nullable TEXT**。
- 归属取值链：① 请求显式 → ② `settings.default_owner`（**默认 `""` 空串**）→ ③ 空。

**会引入的未定义行为**：
1. **`""` 与 `NULL` 与 `'待补充'` 三态混用**：默认 `default_owner=""` 会让新数据的 `owner=''`。A 的 `contributor_summary` 有 `unassigned` 计数，但**未定义 `''` 是否算 unassigned**——若只判 `NULL`/`'待补充'`，空串会被当成"已归属"。
2. **验收可被绕过**：P-09 验收写"非'待补充'"。**空串 `''` 也"非'待补充'"** → 一个 `owner=''` 的新导入会让验收**假通过**，而实际"未指定"。
3. **NOT NULL 冲突**：E7 声明 `created_by: str | null`，但列是 `NOT NULL`；A 说"缺省取…再缺省'待补充'"只覆盖了"字段缺失"，**未覆盖客户端显式传 `null`** 的情况。

**结论**：**该口径必须先定死，否则引入未定义行为。建议——**
1. 定义**唯一"未指定"哨兵**（推荐沿用 `'待补充'`，与既有 `created_by` 一致），`default_owner` 缺省即为 `'待补充'`（**不用空串**）；`owner=''`/`NULL` 一律归一为 `'待补充'` 后再入库。
2. `contributor_summary.unassigned` 明确判 `IN (NULL, '', '待补充')`，与 `MISSING_SENTINELS`（`query.py:485-491`）口径对齐。
3. 验收改为"**已配置 `default_owner` 为具体人名**时，新导入的 `owner` 等于该人名（非空、非'待补充'）"；并单列"未配置时如实显示'未指定'"的对照用例，避免空串假通过。
4. E7 显式规定：`created_by` 传 `null` 或缺失 → 落 `'待补充'`（满足 NOT NULL）。
